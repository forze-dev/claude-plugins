# Working in this repository

A static landing on Astro 7: one content page, a privacy policy, a thank-you
page and a 404. A request form delivered to Telegram through a PHP back end
for Apache / cPanel. One config everything else is derived from.

The project was created by the `landing@forze` plugin, but it is fully
self-contained: everything needed for further work is in this file, in
`docs/` and in the `.claude/commands/` commands. The plugin is not required.

## Running

```bash
npm ci             # ci, not install — exact versions from the lock file
npm run dev        # http://localhost:4321 — the form works if PHP 8.1+ is installed
npm run build      # build into dist/ together with form.php and .htaccess
npm run preview    # serves dist/ (no PHP, no .htaccess)
npm run check      # pre-launch check of dist/ — AFTER build
npm run pack       # release/<domain>.zip — the archive for public_html, AFTER check
npm run test:phone # phone mask: real character-by-character typing
```

## Mandatory rules

These are not style preferences. Breaking any of them is a defect, not a
matter of taste.

### 1. Language

**Talk to the developer in <!-- forze:lang -->English<!-- /forze:lang -->.**
Task files in `docs/tasks/`, changelog entries in `docs/changelog/` and every
reply are written in that language.

This file, the templates in `docs/` and code comments stay **English** — they
are rules and reference for the agent and are not translated per project.

Not affected by this rule:

- names of files, classes, variables, functions and branches;
- commit messages (English, by convention);
- the visible text of the site itself — its language is set by `SITE.lang`,
  `messages` and `ui` in `src/site.config.js` and by the page content.

To change the conversation language, edit the value between the `forze:lang`
markers above.

### 2. The `temp/` folder — incoming materials

Everything raw from the client goes here: mockups, the brief, references,
images, favicons. The structure is arbitrary — the agent sorts it. **Read
`temp/` first**, before asking questions: what's there replaces some of them.

| What | Where |
| --- | --- |
| Photos, illustrations | `public/assets/images/` |
| SVG icons | `public/assets/icons/` |
| OG images 1200×630 | `public/assets/seo/` |
| Favicons | `public/` (root, keep the file names) |

**Never put files into `dist/`.** It is generated by `npm run build` and
overwritten entirely.

Images are compressed and given meaningful Latin names before they move.
Originals stay in `temp/` — the folder is git-ignored. Credentials never go in
`temp/`: `.env` lives outside the repository. Full description in
`temp/README.md`.

### 3. Documentation before code

Work doesn't start until it is written down in `docs/tasks/<slug>.md` from the
template `docs/tasks/_TEMPLATE.md`. A task is split into stages; each stage has
a ready prompt for the implementing agent and a checklist that must pass
**before** the next stage starts.

**After every stage**, no exceptions:

1. write a detailed entry in `docs/changelog/DD.MM.YYYY.md` (one file per day —
   if today's file exists, append to it);
2. add a line to `docs/changelog/changelog.md`;
3. **if there is a `.git` folder at the project root** — commit, naming the task
   and the stage. **If there is no `.git`** — run no git commands at all; mark
   the changelog entry `[stage N]`, and that's enough. When git appears,
   `git init` and a first commit are all it takes — the rule switches itself.

When a task is closed, move its file to `docs/archive/` with a note at the top:
when and why it was closed. Full description in `docs/README.md`.

### 4. Determinism

The same input must give the same result. Every time.

- **Never invent facts.** A phone, address, price, opening hours, a review or a
  "200+ clients" figure that isn't in `site.config.js` or in the brief is asked
  for, not assumed.
- **No randomness in generated content.** No `Math.random()`, no ids from
  `Date.now()`, no shuffling.
- **No network requests during the build.**
- **Dependencies stay pinned.** Don't widen version ranges.
- **This is verifiable — so verify it.** Two consecutive builds must produce a
  byte-identical `dist/`, and `npm run pack` an identical zip.

The one deliberate exception is the copyright year, taken from the build date.

### 5. One page per session

**At most one page** is built per session. A page is the `.astro` file, its
styles, its content, its structured data in **both** formats, and its check.

The landing is one page, even if a long one. A new page (services, pricing,
portfolio) is a separate session and a separate stage in the task file.

### 6. Dependency audit

**`npm audit` — at the start of every project and before every delivery.** A
pinned version guarantees **sameness** of the build, not its **safety**.

- **Clean** — one line in the changelog.
- **Findings** — don't run `npm audit fix --force` blindly. Read each advisory
  and assess whether the vector is reachable in a static build with no user
  input in rendering.
- **The vector is real** — stop and discuss the upgrade with the developer.
- **The vector is unreachable** — record in the changelog which CVE it is, why
  it doesn't apply, and under what condition that assessment stops holding.

`npm audit fix` without `--force` only changes transitive dependencies within
their allowed ranges and leaves the direct pins alone. It may be applied, but
only followed by verification: `npm ci`, `build`, `check`, comparing two builds.

### 7. Both structured-data formats

Every entity is described **twice**: as JSON-LD and as microdata. Details in
the "Structured data" section.

## The main rule about data

**Nothing that changes from project to project may be hard-coded in a page or
a component.**

Contacts, domain, brand name, menu, opening hours, messengers, form limits and
interface strings (`ui`) live in `src/site.config.js`. The header, footer,
modal, every JSON-LD block, the microdata, `robots.txt`, the web manifest,
`form.limits.json` and `.htaccess` read from it and are rendered **at build
time**.

The exception is page copy: headings, paragraphs, section items, FAQ answers.
That is content, and it belongs in the page.

## Landing and sections

`src/pages/index.astro` is built from the sections in `src/components/sections/`:

| Section | For | Data |
| --- | --- | --- |
| `Hero` | first screen, the only h1 | `title`, `lead`, `facts`, `secondary`, `image` |
| `Cards` | advantages, services, "who it's for" | `items: {title, body, price?, icon?}`, `columns` |
| `Steps` | how we work | `items: {title, body}` |
| `Section` + `Faq` | questions and answers | array of `{question, answer}` |
| `Section` + `Gallery` | photos of work | `items: {src, alt, caption?, width, height}` |
| `Testimonials` | **real** reviews only | `items: {quote, author, role?}` |
| `Cta` | call-to-action band | `title`, `text` |
| `Contacts` | contacts + form, anchor `#contacts` | from the config |

Rules:

- A section's `id` is a menu anchor. A `SITE.nav` item looks like `/#id` (with
  the slash — so the menu also works from the privacy page).
- A section's styles are imported by the section component itself
  (`src/styles/sections/`), so only the CSS of sections in use is built.
- A new section is a new component in `sections/` plus its CSS. The
  `/add-section` command describes how.
- The `data-demo-content` attribute marks scaffold demo copy. `npm run check`
  won't pass while it remains.

## Third-party scripts

Google Tag Manager and GA4 have dedicated fields: `analytics.gtmId` or
`analytics.gaId` in `src/site.config.js`. They are injected **only in the
production build**. Use one — Tag Manager already contains GA4.

Everything else goes in `src/components/Analytics.astro` (site-wide) or through
the layout's `head` slot (one page). `is:inline` is mandatory.

**Close `<noscript>` explicitly.** The parser doesn't treat `<noscript … />` as
self-closing — everything below it in the template becomes its content.

Added a tracker or a widget — update section 8 of the privacy policy.

## Structured data — two formats, one entity

Each page describes its entities **twice**: JSON-LD in `<head>` and microdata
(`itemscope` / `itemprop`) on the markup.

**1. `itemid` equals `@id`.** The root of the business microdata carries
`itemid={ids.organization}` from `src/lib/schema.js`.

**2. Both formats read one source.** Values come from `site.config.js` and from
the same arrays the page renders. Never type a value into an `itemprop` by hand.

### What is marked up where

| Entity | Microdata | JSON-LD |
| --- | --- | --- |
| Business (`SITE.businessType`) | `Footer.astro`, with `itemid` — **one node per page** | `business()`, added by the layout |
| `FAQPage` | `Faq.astro` | `faqPage(entries)` on the page |
| `BreadcrumbList` | `Breadcrumbs.astro` (inner pages) | `breadcrumbs(trail)` |
| `ImageGallery` | `Gallery.astro` | — |

- **The business is one node per site.** Its JSON-LD is added by the layout
  (`Base.astro`), its microdata by the footer. A page never adds `business()`
  itself. The properties of `business()` and of the footer match one to one:
  phone — E.164 in a `<meta>`, address — `PostalAddress`, description —
  `SITE.description`. Added a property in one place — add it in the other.
- **The contacts section has no microdata** — the footer already carries the
  full description.
- Geo and hours are output **only** when `SITE.businessType` is not
  `Organization`. The `isPlace` flag is exported by `site.config.js`.
- The menu and reviews have no structured data on purpose: they give no rich
  results, and Google doesn't show a business's reviews of itself.
- `thank-you` and `404` (layout `Bare`, `noindex`) have no structured data at all.

## Where things go

| What you change | File |
| --- | --- |
| Contact, menu item, domain, form limit, interface string | `src/site.config.js` |
| Color, size, spacing, radius | `src/styles/base/variables.css` |
| A landing section | `src/components/sections/<Name>.astro` + `src/styles/sections/<name>.css` |
| Something reused across the site | `src/components/<Name>.astro` + `src/styles/components/<name>.css` in `main.css` |
| Something on one page only | `src/styles/pages/<page>.css`, imported by the page |
| Client-side behaviour | `src/scripts/` |
| Shape of structured data | `src/lib/schema.js` |
| Apache rules | `server/htaccess.template` (not `dist/.htaccess`) |

## Adding a page

The `/add-page` command. In short: `src/pages/<slug>.astro` on the `Base`
layout, `title` and `description`, `schema` — an **array** of the page's own
nodes (not `graph(...)`), `<Breadcrumbs trail={trail} />` and the same `trail`
in `breadcrumbs(trail)`. The reference inner page is `privacy-policy.astro`.
The route, sitemap entry and canonical appear on their own.

## URLs

`build.format: 'file'` outputs `privacy-policy.html`, served at
`/privacy-policy`. During the build `Astro.url.pathname` is
`/privacy-policy.html` — always normalize it with `cleanPath()` from
`src/lib/path.js`. Never link to `.html`.

## The form

- `src/components/RequestForm.astro` — the markup, in the contacts section
  **and** in the modal. There is never a second copy. Instance `id`s differ.
- `src/scripts/form.js` — mask, validation, submission.
- `server/form.php` — the only back end. `npm run build` puts it into the
  build (`dist/scripts/`) together with `form.limits.json`.

**Limits are never retyped by hand.** The single source is `SITE.form`: the
browser reads it directly, PHP via `form.limits.json` (`tools/limits.mjs`),
`.htaccess` via the substitution in `tools/build.mjs`. Messages mentioning the
file size use `{size}` and `{types}` (`fillMessage`).

**Locally** the dev server starts `php -S` on `server/` and proxies form
requests to it (`astro.config.mjs`). Without PHP the form answers 503 in dev
with an explanation; the rest of the site works. In dev, `.env` lives at the
project root.

### Order of checks in `form.php`

1. **honeypot** — the `company` field must be empty;
2. **fill duration** — `elapsedMs` is required and numeric;
3. **Origin/Referer** — the request comes from our domain (against abuse from
   other sites in a browser; a script outside a browser fakes the header —
   so this is not the main defence);
4. **file** — size, non-empty, extension, signature;
5. **rate limit** — one request per IP per `form.rateLimitSeconds` (after the
   file, so a file mistake doesn't block a retry);
6. **credentials** — only now, so a bot never learns whether the form is configured.

Three things that are easy to break again:

- `elapsedMs` is a **duration** from `performance.now()`, not a timestamp.
- A missing or non-numeric `elapsedMs` is **rejected**.
- The file type is decided by its **signature** (first bytes) against the
  `form.signatures` table, not by the MIME type from the browser.

**Don't touch the mask without `npm run test:phone`.** Typing is emulated
character by character, and **values** are compared. The key invariant is
idempotence: `formatPhone(formatPhone(x)) === formatPhone(x)`. Formatting is
one function, `formatNational` in the config, for both the mask and the
visible numbers.

## Things that look like bugs but aren't

- `/thank-you` redirects to `/` when opened without fresh `formStatus` and
  `timestamp`.
- `public/assets/seo/` is empty. The client provides OG images.
- The modal's markup is in the DOM on every page, hidden.
- `npm run preview` runs no PHP and reads no `.htaccess`: the form doesn't work
  there, and `/privacy-policy.html` returns 200 instead of a redirect. That is
  checked on the hosting.
- `scrollbar-gutter: stable` in `reset.css` is not cosmetic: without it, scroll
  locking makes the fixed header jump.
- `.htaccess` redirects to HTTPS — the domain must have SSL (AutoSSL on
  cPanel). Without a certificate the redirect "breaks" the site.

## Versions

Versions in `dependencies` are **exact numbers, no `^`**. Install with
`npm ci`. Pinned: `astro 7.3.5`, `@astrojs/sitemap 3.7.4`.

Astro 7 requires **Node 22.12+**. The PHP back end needs **PHP 8.1+** (on the
hosting; locally — to test the form).

### Dependency security

As of 2026-10-17 `npm audit` is **clean**: the lock file was updated with patch
versions of the transitive `sharp`, `source-map-js` and `http-cache-semantics`;
the direct pins did not change. That's no reason to skip the check — rule 6.

If the audit ever shows a finding that can't be closed: there is no SSR, no
adapter, no server islands, no `astro:assets` and no user input in rendering
here. Added any of these — the previous assessment no longer holds.

## Pre-launch check

`npm run check` (`tools/check.mjs`) reads the built `dist/` and fails if
something that must not reach the client is left: scaffold placeholder values,
`data-demo-content`, a missing OG image, a page without `canonical`, broken
`ld+json`, a duplicate `id`, a broken local link, `robots.txt` without
`Sitemap:`, missing `form.php` / `form.limits.json` / `.htaccess`, `.env` in
the build.

**On the unfilled scaffold it fails on purpose.** Every message names **the
file, the problem and the fix** — keep that format.

The check can't be replaced by eyeballing: `build` → `check` → `pack` before
every delivery.

## Code style

Tabs for indentation. Comments explain **why**, not **what**. A simple
function and a data attribute beat a new abstraction.
