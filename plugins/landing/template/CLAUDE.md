# Робота в цьому репозиторії

Статичний лендинг на Astro 7: одна контентна сторінка, політика
конфіденційності, сторінка подяки й 404. Форма заявки з доставкою в Telegram
через PHP-бекенд для Apache / cPanel. Один конфіг, з якого виводиться все
решта.

Проєкт створено плагіном `landing@forze`, але він повністю самодостатній: усе,
що потрібно для подальшої роботи, — у цьому файлі, у `docs/` і в командах
`.claude/commands/`. Плагін для роботи не потрібен.

## Запуск

```bash
npm ci             # саме ci, не install — точні версії з lock-файла
npm run dev        # http://localhost:4321 — форма працює, якщо встановлено PHP 8.1+
npm run build      # збірка в dist/ разом із form.php і .htaccess
npm run preview    # віддає dist/ (без PHP і без .htaccess)
npm run check      # передзапускова перевірка dist/ — ПІСЛЯ build
npm run pack       # release/<домен>.zip — архів для public_html, ПІСЛЯ check
npm run test:phone # маска телефону: реальний посимвольний набір
```

## Обов'язкові правила

Це не стильові вподобання. Порушення будь-якого з них — дефект, а не питання
смаку.

### 1. Мова

**З розробником спілкуємося українською.** Уся документація в `/docs`, усі
коментарі в коді, `README.md`, `CLAUDE.md` і файли задач — теж українською.

Винятки, які українською **не** перекладаються:

- імена файлів, класів, змінних, функцій і гілок;
- повідомлення комітів (англійською, як прийнято);
- видимий текст самого сайту — його мова задається `SITE.lang`, `messages` і
  `ui` у `src/site.config.js` та контентом сторінок.

Якщо на старті проєкту обрано іншу мову спілкування, це правило переписане під
неї, і документація ведеться нею.

### 2. Тека `temp/` — вхідні матеріали

Сюди кладуть усе сире від клієнта: макети, бриф, референси, зображення,
фавікони. Структура довільна — розкладає агент. **Читай `temp/` першою**, ще до
питань: те, що там лежить, заміняє частину питань.

| Що | Куди |
| --- | --- |
| Фото, ілюстрації | `public/assets/images/` |
| Іконки SVG | `public/assets/icons/` |
| OG-зображення 1200×630 | `public/assets/seo/` |
| Фавікони | `public/` (у корінь, імена не змінювати) |

**Ніколи не клади файли в `dist/`.** Ця тека генерується `npm run build` і
перезаписується повністю.

Зображення перед перенесенням стискаються й отримують осмислені імена
латиницею. Оригінали лишаються в `temp/` — тека в `.gitignore`. Доступам у
`temp/` не місце: `.env` живе поза репозиторієм. Повний опис — у
`temp/README.md`.

### 3. Документація до коду

Робота не починається, доки її не записано в `docs/tasks/<slug>.md` за
шаблоном `docs/tasks/_TEMPLATE.md`. Задача ділиться на етапи; кожен етап має
готовий промпт для агента-виконавця і чекліст перевірки, що має пройти **до**
початку наступного етапу.

**Після кожного етапу**, без винятків:

1. пишемо детально в `docs/changelog/ДД.ММ.РРРР.md` (один файл на день — якщо
   файл за сьогодні вже є, дописуємо в нього);
2. додаємо рядок в `docs/changelog/changelog.md`;
3. **якщо в корені проєкту є `.git`** — робимо коміт, називаючи в ньому задачу
   й етап. **Якщо `.git` немає** — git-команд не виконуємо взагалі; запис у
   ченжлозі позначаємо `[етап N]`, і цього досить. Коли git з'явиться,
   достатньо `git init` і першого коміту — правило перемкнеться само.

Коли задача закрита — переносимо файл у `docs/archive/` з приміткою зверху:
коли і чому закрито. Повний опис — у `docs/README.md`.

### 4. Детермінованість

Однакові вхідні дані мають давати однаковий результат. Щоразу.

- **Ніколи не вигадувати факти.** Телефон, ціна, адреса, години роботи, відгук
  чи цифра «200+ клієнтів», яких немає в `site.config.js` або в брифі, —
  питаються, а не домислюються.
- **Жодної випадковості у згенерованому контенті.** Ніяких `Math.random()`,
  ідентифікаторів від `Date.now()`, перемішування.
- **Жодних мережевих запитів під час збірки.**
- **Залежності лишаються запінованими.** Не розширювати діапазон версій.
- **Це перевіряється — тож перевіряй.** Дві послідовні збірки мають дати
  байт-у-байт ідентичний `dist/`, а `npm run pack` — ідентичний zip.

Єдиний свідомий виняток — рік у копірайті, він береться з дати збірки.

### 5. Одна сторінка за сесію

За сесію верстається **максимум одна сторінка**. Сторінка — це файл `.astro`,
її стилі, контент, структуровані дані в **обох** форматах і перевірка.

Лендинг — це одна сторінка, хоч і довга. Нова сторінка (послуги, прайс,
портфоліо) — окрема сесія й окремий етап у файлі задачі.

### 6. Аудит залежностей

**`npm audit` — на старті кожного проєкту й перед кожною здачею.** Запінована
версія гарантує **однаковість** збірки, а не її **безпеку**.

- **Чисто** — рядок у ченжлог.
- **Є знахідки** — не запускати `npm audit fix --force` наосліп. Прочитати
  кожну advisory й оцінити, чи вектор досяжний у статичній збірці без
  користувацького вводу в рендер.
- **Вектор реальний** — зупинитися й обговорити оновлення з розробником.
- **Вектор недосяжний** — записати в ченжлог, який саме це CVE, чому не
  застосовний і за якої умови оцінка перестане діяти.

`npm audit fix` без `--force` міняє лише транзитивні залежності в межах
дозволених діапазонів і прямі піни не чіпає. Його можна застосувати, але лише
з подальшою перевіркою: `npm ci`, `build`, `check`, порівняння двох збірок.

### 7. Обидва формати структурованих даних

Кожна сутність описується **двічі**: як JSON-LD і як мікророзмітка. Деталі —
у розділі «Структуровані дані».

## Головне правило про дані

**Нічого, що змінюється від проєкту до проєкту, не можна вписувати в сторінку
чи компонент руками.**

Контакти, домен, назва бренду, меню, години роботи, месенджери, обмеження
форми й службові рядки інтерфейсу (`ui`) живуть у `src/site.config.js`.
Хедер, футер, модалка, всі блоки JSON-LD, мікророзмітка, `robots.txt`,
веб-маніфест, `form.limits.json` і `.htaccess` читають звідти й рендеряться
**під час збірки**.

Виняток — текст сторінок: заголовки, абзаци, пункти секцій, відповіді FAQ. Це
контент, і його місце в сторінці.

## Лендинг і секції

`src/pages/index.astro` складається із секцій `src/components/sections/`:

| Секція | Для чого | Дані |
| --- | --- | --- |
| `Hero` | перший екран, єдиний h1 | `title`, `lead`, `facts`, `secondary`, `image` |
| `Cards` | переваги, послуги, «для кого» | `items: {title, body, price?, icon?}`, `columns` |
| `Steps` | етапи роботи | `items: {title, body}` |
| `Section` + `Faq` | питання й відповіді | масив `{question, answer}` |
| `Section` + `Gallery` | фото робіт | `items: {src, alt, caption?, width, height}` |
| `Testimonials` | **лише справжні** відгуки | `items: {quote, author, role?}` |
| `Cta` | смуга заклику до дії | `title`, `text` |
| `Contacts` | контакти + форма, якір `#contacts` | з конфіга |

Правила:

- `id` секції — це якір меню. Пункт у `SITE.nav` має вигляд `/#id` (зі слешем
  — щоб меню працювало й зі сторінки політики).
- Стилі секції імпортує сам компонент секції (`src/styles/sections/`), тож у
  збірку потрапляє CSS лише використаних секцій.
- Нова секція — новий компонент у `sections/` + свій CSS. Команда
  `/add-section` описує, як.
- Атрибут `data-demo-content` позначає демо-текст шаблону. `npm run check` не
  пропустить збірку, доки він лишається.

## Сторонні скрипти

Для Google Tag Manager і GA4 є окремі поля: `analytics.gtmId` або
`analytics.gaId` у `src/site.config.js`. Вони підставляються **тільки в
production-збірці**. Використовуй щось одне — Tag Manager уже містить GA4.

Усе інше — у `src/components/Analytics.astro` (на весь сайт) або через слот
`head` у layout (для однієї сторінки). `is:inline` обов'язковий.

**`<noscript>` закривай явно.** Запис `<noscript … />` парсер самозакривним не
вважає — усе, що йде в шаблоні нижче, стає його вмістом.

Додав трекер чи віджет — онови розділ 8 політики конфіденційності.

## Структуровані дані — два формати, одна сутність

Кожна сторінка описує свої сутності **двічі**: JSON-LD у `<head>` і
мікророзмітка (`itemscope` / `itemprop`) на розмітці.

**1. `itemid` збігається з `@id`.** Корінь мікророзмітки бізнесу несе
`itemid={ids.organization}` із `src/lib/schema.js`.

**2. Обидва формати читають одне джерело.** Значення — з `site.config.js` і з
тих самих масивів, які рендерить сторінка. Ніколи не вписуй значення в
`itemprop` руками.

### Що і де розмічено

| Сутність | Мікророзмітка | JSON-LD |
| --- | --- | --- |
| Бізнес (`SITE.businessType`) | `Footer.astro`, з `itemid` — **один вузол на сторінку** | `business()`, додає layout |
| `FAQPage` | `Faq.astro` | `faqPage(entries)` на сторінці |
| `BreadcrumbList` | `Breadcrumbs.astro` (внутрішні сторінки) | `breadcrumbs(trail)` |
| `ImageGallery` | `Gallery.astro` | — |

- **Бізнес — один вузол на сайт.** Його JSON-LD додає layout (`Base.astro`),
  мікророзмітку — футер. Сторінка ніколи не додає `business()` сама.
  Властивості `business()` і футера збігаються одна в одну: телефон — E.164 у
  `<meta>`, адреса — `PostalAddress`, опис — `SITE.description`. Додав
  властивість в одне місце — додай і в інше.
- **Секція контактів мікророзмітки не має** — повний опис уже несе футер.
- Гео й години виводяться **лише** коли `SITE.businessType` не
  `Organization`. Прапорець `isPlace` експортує `site.config.js`.
- Меню й відгуки — без структурованих даних свідомо: rich results вони не
  дають, а відгуки бізнесу про себе Google не показує.
- На `thank-you` і `404` (layout `Bare`, `noindex`) структурованих даних немає
  взагалі.

## Додавання сторінки

Команда `/add-page`. Коротко: `src/pages/<slug>.astro` на layout `Base`,
`title` і `description`, `schema` — **масив** власних вузлів (не `graph(...)`),
`<Breadcrumbs trail={trail} />` і той самий `trail` у `breadcrumbs(trail)`.
Зразок внутрішньої сторінки — `privacy-policy.astro`. Маршрут, sitemap і
canonical з'являються самі.

## URL-и

`build.format: 'file'` віддає `privacy-policy.html` за адресою
`/privacy-policy`. Під час збірки `Astro.url.pathname` дорівнює
`/privacy-policy.html` — завжди нормалізуй через `cleanPath()` з
`src/lib/path.js`. Ніколи не посилайся на `.html`.

## Форма

- `src/components/RequestForm.astro` — розмітка, у секції контактів **і** в
  модалці. Другої копії не буває. `id` екземплярів різні.
- `src/scripts/form.js` — маска, валідація, надсилання.
- `server/form.php` — єдиний бекенд. У збірку (`dist/scripts/`) його кладе
  `npm run build` разом із `form.limits.json`.

**Ліміти не переписуються руками.** Єдине джерело — `SITE.form`: браузер
читає його напряму, PHP — з `form.limits.json` (`tools/limits.mjs`), `.htaccess`
— через заміну в `tools/build.mjs`. Тексти з розміром файла підставляють
`{size}` і `{types}` (`fillMessage`).

**Локально** dev-сервер піднімає `php -S` на `server/` і проксує туди запити
форми (`astro.config.mjs`). Без PHP форма в dev відповідає 503 з поясненням,
решта сайту працює. `.env` для dev лежить у корені проєкту.

### Порядок перевірок у `form.php`

1. **honeypot** — поле `company` має бути порожнім;
2. **тривалість заповнення** — `elapsedMs` обов'язкове й числове;
3. **Origin/Referer** — запит з нашого домену (від браузерного зловживання;
   скрипт поза браузером заголовок підробляє — тому це не основний захист);
4. **файл** — розмір, непорожність, розширення, сигнатура;
5. **rate limit** — один запит на IP за `form.rateLimitSeconds` (після файла,
   щоб помилка з файлом не блокувала повторну спробу);
6. **креденшили** — аж тепер, щоб бот не дізнався, чи форма налаштована.

Три речі, які легко зламати назад:

- `elapsedMs` — **тривалість** із `performance.now()`, а не мітка часу.
- Відсутнє або нечислове `elapsedMs` **відхиляється**.
- Тип файла визначається **сигнатурою** (перші байти) за таблицею
  `form.signatures`, а не MIME-типом від браузера.

**Маску не чіпай без `npm run test:phone`.** Набір емулюється посимвольно, і
звіряються **значення**. Головний інваріант — ідемпотентність:
`formatPhone(formatPhone(x)) === formatPhone(x)`. Форматування — одна функція
`formatNational` у конфізі, і для маски, і для видимих номерів.

## Те, що виглядає як баг, але ним не є

- `/thank-you` редіректить на `/`, якщо відкрита без свіжих `formStatus` і
  `timestamp`.
- `public/assets/seo/` порожня. OG-зображення постачає замовник.
- Розмітка модалки є в DOM на кожній сторінці, прихована.
- `npm run preview` не виконує PHP і не читає `.htaccess`: форма там не
  працює, а `/privacy-policy.html` віддасть 200 замість редіректу. Це
  перевіряється вже на хостингу.
- `scrollbar-gutter: stable` у `reset.css` — не косметика: без нього блокування
  прокрутки смикає фіксований хедер.
- `.htaccess` переадресовує на HTTPS — на домені має бути SSL (AutoSSL на
  cPanel). Без сертифіката сайт «зламається» редіректом.

## Версії

Версії в `dependencies` записані **точними числами, без `^`**. Ставимо через
`npm ci`. Запіновано: `astro 7.3.5`, `@astrojs/sitemap 3.7.4`.

Astro 7 вимагає **Node 22.12+**. PHP-бекенд — **PHP 8.1+** (на хостингу; локально
— для перевірки форми).

### Безпека залежностей

Станом на 17.10.2026 `npm audit` **чистий**: lock-файл оновлено патч-версіями
транзитивних `sharp`, `source-map-js` і `http-cache-semantics`, прямі піни не
змінювались. Це не привід не перевіряти — правило 6.

Якщо аудит покаже знахідку, яку не можна закрити: тут немає SSR, адаптера,
server islands, `astro:assets` і користувацького вводу в рендер. Додав щось із
цього — попередня оцінка не діє.

## Передзапускова перевірка

`npm run check` (`tools/check.mjs`) читає зібраний `dist/` і падає, якщо в ньому
лишилося те, що не має доїхати до клієнта: значення-заглушки з шаблону,
`data-demo-content`, відсутнє OG-зображення, сторінка без `canonical`, зламаний
`ld+json`, дублікат `id`, битий локальний лінк, `robots.txt` без `Sitemap:`,
відсутні `form.php` / `form.limits.json` / `.htaccess`, `.env` у збірці.

**На незаповненому шаблоні вона падає навмисно.** Кожне повідомлення називає
**файл, проблему і спосіб виправлення** — тримайся цього формату.

Перевірку не можна замінити оком: `build` → `check` → `pack` перед кожною
здачею.

## Стиль коду

Відступи — табуляція. Коментарі пояснюють **чому**, а не **що**. Проста функція
й data-атрибут кращі за нову абстракцію.
